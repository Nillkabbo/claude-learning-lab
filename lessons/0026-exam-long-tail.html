Lesson 0026 · Exam gap filler

The long tail: six exam topics you need

Task statements the course missed — each one is worth points on exam day.

≈ 15 minutes Covers: 1.5 · 1.7 · 3.3 · 4.6 · 5.5 · 2.2

The official exam guide lists 30 task statements. The course covers 24 well. These six slipped through — each is testable, each is practical, and none takes more than a few minutes to learn.

1. Agent SDK hooks (Task 1.5)

What it is: The Agent SDK exposes the same lifecycle events as Claude Code hooks — PreToolUse, PostToolUse, Stop — but as programmatic callbacks in your code rather than shell scripts.

# In the Agent SDK
for await (const message of query({
  prompt: "Process the refund",
  options: {
    hooks: {
      PostToolUse: async (event) => {
        // Normalize tool output before it reaches the model
        if (event.tool_name === "get_refund") {
          event.output = normalizeCurrency(event.output);
        }
      },
      PreToolUse: async (event) => {
        // Block refunds over $500
        if (event.tool_name === "process_refund" &&
            event.input.amount > 500) {
          return { block: true, reason: "Requires human approval" };
        }
      }
    }
  }
})) { ... }

Exam scenario shape: "Your agent processes refunds. How do you intercept calls over $500 before they execute?" → PreToolUse hook that returns block:true.

2. Session forking and named resume (Task 1.7)

What it is: The Agent SDK supports fork_session() — creating a new session that inherits the full conversation history — and --resume <session-name> for named session continuity.

  • Fork: one session branches into two, each continuing independently. Useful for exploring alternatives without polluting the original.
  • Named resume: pick up exactly where a named session left off — not just "the most recent" (-c) but a specific one (-r or --resume <name>).

Exam scenario shape: "Your research agent has a promising partial result. How do you explore two different continuations?" → fork the session, run each branch with a different approach, keep whichever succeeds.

3. Path-specific rules and @import (Task 3.1/3.3)

What it is: Beyond the CLAUDE.md scope ladder, Claude Code supports:

  • @import: a CLAUDE.md can import other files: @docs/api-conventions.md pulls that file's content into the memory.
  • .claude/rules/ with paths: frontmatter: rules that load only when Claude reads files matching a path pattern.
    # .claude/rules/python-style.md
---
paths: ["**/*.py", "**/tests/**"]
---
Use pytest. fixtures over mocks. 88-char lines.

Exam scenario shape: "Your monorepo has different conventions for Python and TypeScript. How do you load only the relevant rules?" → path-scoped rules in .claude/rules/ with paths frontmatter.

4. Multi-instance review architectures (Task 4.6)

What it is: For high-stakes output, run multiple independent review passes and reconcile. The official guide's named patterns:

  • Self-review: the same model reviews its own output. Cheapest, but shares blind spots with the generator.
  • Independent instances: separate model instances (different seeds, or different models) review the same output. Catches what self-review misses.
  • Per-file + cross-file passes: one review checks each file in isolation; another checks cross-file consistency (imports, naming, API contracts).

The limitation the exam tests: Self-review alone is unreliable — "a model cannot reliably find its own errors." Independent instances or cross-model review are the fix.

Exam scenario shape: "Your code-generation agent produces multi-file changes. How do you catch cross-file inconsistencies?" → run independent review instances: one per-file, one cross-file, then reconcile before merging.

5. Confidence calibration and stratified sampling (Task 5.5)

What it is: When a model outputs field-level confidence scores, those scores need calibration — verifying that "80% confident" actually means 80% correct. The official approach:

  1. Have the model output confidence per field.
  2. On a labeled validation set, measure actual accuracy at each confidence level.
  3. Stratify: sort outputs by confidence; route high-confidence to auto-accept, low-confidence to human review.
  4. Tune the threshold based on your precision/recall needs.

Exam scenario shape: "Your extraction pipeline outputs confidence scores, but '90% confident' fields are only 70% accurate. What do you do?" → calibrate against a labeled set, stratify the review threshold, tune for the acceptable error rate.

6. Structured error metadata (Task 2.2)

What it is: Beyond the text-based error taxonomy from 0007, the exam tests structured metadata on tool errors:

{
  "type": "tool_result",
  "tool_use_id": "toolu_01",
  "is_error": true,
  "content": "Rate limit exceeded. Retry after 30 seconds.",
  "metadata": {
    "errorCategory": "transient",
    "isRetryable": true,
    "retryAfterSeconds": 30
  }
}

The exam angle: the model reads the text, but your orchestration code reads the metadata — it decides whether to retry, escalate, or reroute based on the structured fields, not by parsing natural language.
