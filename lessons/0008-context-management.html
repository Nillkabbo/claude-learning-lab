Lesson 0008 · Phase 2 — Tools & context (final lesson of the phase)

Context management: windows, compaction, and what you keep

Statelessness made you the owner of the conversation. Ownership turns out to be a budget problem.

≈ 15 minutes Exam: Context Management · 15% No coding needed
Grow → trigger → save essentials to memory → clear with placeholders → continue: the budget that rots, managed.

Lesson 0001's law — the API is stateless, your code owns the conversation — was a curiosity then. Now it's an architecture problem: long-running agents accumulate tool results, documents, and thinking, and everything you keep competes for one window. This 15% domain is the craft of deciding what stays.

The budget box

What counts toward the context window: the system prompt, all messages — including tool results, images, and documents — plus tool definitions and the current output. Two surcharges people forget:

  • Thinking blocks persist on newer models. Opus 4.5+ and Sonnet 4.6+ keep prior thinking in history — re-billed as input on every later turn (earlier tiers and Haiku auto-strip them).
  • Cached tokens still count. Prompt caching "changes what you pay for those tokens, not whether they count" toward the window.

Current windows: 1M tokens is the default on current models (Opus 5, Sonnet 5, Fable 5, Mythos 5…), 200K on the previous generation, with max output of 128K. And the overflow rules differ — memorize both:

  • Input alone exceeds the window → 400 error ("prompt is too long"), on all models.
  • Input + max_tokens overflows on Claude 4.5+ → accepted, then generation stops gracefully with stop_reason: "model_context_window_exceeded".
Context rot — why 1M isn't permission to hoard As tokens grow, "accuracy and recall degrade, a phenomenon known as context rot." The docs' framing is the exam's framing: context is a finite resource with diminishing returns — irrelevant content degrades model focus. A big window is headroom for good curation, not an excuse to skip it.

Two fine prints that make good exam questions: clearing tool results invalidates cached prefixes — which is exactly why clear_at_least exists (don't torch the cache to save a trickle); and every response reports applied_edits, so you can observe what was cleared.

Stale data, and the strategies above the API

Context strategies also fight staleness: cleared-with-placeholder keeps history honest about what's gone; memory files persist what matters; and retrieval (RAG) grounds answers in current sources fetched fresh rather than aged context. For very long horizons, Anthropic's engineering guidance (the "Effective context engineering" post below) rounds out the same toolkit with structured note-taking and sub-agent architectures — fresh contexts doing focused work, returning only results. That pattern gets its own lesson in Phase 4.

Exercise — spec the shift agent's context (exam-style)

An Apex ops agent runs 8-hour shifts on Sonnet 5 (1M window). It calls web_search and a 6,000-token read_manual tool constantly, must remember client escalations for weeks, and finance is loud about token spend. It also has 40 tool definitions loaded.

On paper: (1) pick your strategy stack and justify each piece; (2) write the context_management config with sensible values; (3) name the two extra moves for the 40-tool bill.

Check your answer

(1) Stack: server-side compaction as the primary strategy (shifts run past any limit, summaries carry the day's thread); tool result clearing for the manual dumps and search noise (placeholder honesty, huge token savings); memory tool enabled alongside, so near-threshold warnings turn client escalations into files that survive for weeks — the multisession pattern; memory is also where "stale vs current" gets managed by re-reading when needed.

(2)

"context_management": {
  "edits": [
    { "type": "clear_thinking_20251015", "keep": "all" },
    { "type": "clear_tool_uses_20250919",
      "trigger": { "type": "input_tokens", "value": 200000 },
      "keep": 3,
      "clear_at_least": 20000 }
  ]
}

Rationale: with 1M tokens, trigger at 200K leaves huge headroom before context rot while keeping cache invalidation rare and worthwhile (clear_at_least 20K); keep: 3 preserves the working set of recent results. (Triggering at the 100K default is also defensible — the justification is what's graded.)

(3) Consolidate the 40 definitions down (0006's consolidation guidance), and/or adopt the tool search tool so definitions load on demand — and use the token counting API to verify the savings.
