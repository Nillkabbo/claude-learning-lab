The review bottleneck

In which the team grows, the queue grows faster, and the PRs start reviewing themselves.

≈ 10 minutes + hands-on Concepts: CI · automated code review · ultrareview Project gains: a pipeline that tests and reviews every PR
Chapter 9 of 12 — the story so far.

The queue

Two more developers joined, and now Tracker — the little tool from your first Monday — has nine open PRs and one bottleneck: humans who review after lunch, if there's lunch. Priya's own PR has been waiting two days. "Fix the queue," she says, "you broke us into this situation, unbreak it."

Machines first

The boring half of the fix is the most valuable: CI. A GitHub Action — one file, .github/workflows/ci.yml — runs on every PR: install Python, run the suite. Suddenly the review queue has a bouncer: red PRs don't even reach a human. You didn't add discipline; you moved it from memory to machinery — the same move as CLAUDE.md-to-permission-rules, one layer up.

The reviewer that doesn't sleep

The second half is Claude Code's own: code review in the pipeline. The Action runs Claude against the diff — headless, JSON out, permission-contained (read-only, strict allow-list, a spend cap — automation gets fences, always) — and posts findings as PR comments: real ones, mostly. It flags a swallowed exception in Dana's PR and an untested edge case in Marco's, and both fixes land before any human looks. The queue's average wait drops from "tomorrow" to "forty minutes."

For the big one — Dana's storage refactor, four hundred lines touching the atomic writes you built in Chapter 2 — you reach for the heavy artillery: ultrareview, the cloud fleet: /code-review ultra spawns a fleet of reviewer agents in remote sandboxes, each auditing the branch in parallel — security, correctness, data-safety. It comes back with two findings. One is wrong. One saves your atomic-write guarantees from a subtle regression that would have haunted Chapter 10's nights. You take the good with the bad and say the thing you now believe: automated review is a first pass, not a verdict — humans read the findings, not just the checkmark.

What just happened, named CI moves "does it work" from opinion to gate. Claude review moves "what does a human notice first" earlier and cheaper. Ultrareview parallelizes deep audits. The human role shifts — from reading diffs to judging findings. That's the whole modern review stack, lived.

Your turn — the chapter's hands-on

Do it in your real repo
  1. Add .github/workflows/ci.yml: on PR, run the test suite. Verify with one deliberately red PR.
  2. Add a Claude review step (headless, read-only allow-list, cost-capped) posting a comment; verify on a real PR.
  3. Introduce one small bug deliberately; confirm the reviewer catches it — then revert.
  4. If on a paid plan: run /code-review ultra on your biggest recent branch; grade its findings — keep the true, dismiss the false, note the ratio.

Checkpoint: red PRs blocked by CI, review comments appearing automatically, one caught bug as evidence. Report it — next chapter, something breaks at 2 a.m. while everyone sleeps, and Tracker is the only one awake.
