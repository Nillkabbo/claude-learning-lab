Pillar 1: CLAUDE.md — context, not enforcement

Claude Code has two memory systems: CLAUDE.md (instructions you write) and auto memory (notes Claude writes itself, indexed in a MEMORY.md). The sentence to memorize — it's an exam question wearing a trenchcoat — is the official one:

The line that separates the layers Memory files are "context, not enforced configuration." Instructions guide; they don't guarantee. Hard enforcement lives in permission rules and hooks — never in CLAUDE.md.

The scope ladder (broadest → most specific):

ScopeLocationUse
Managed policyorg-managed path (e.g., /Library/Application Support/ClaudeCode/)Org-wide rules
User~/.claude/CLAUDE.mdYour preferences, every project
Project./CLAUDE.md (or ./.claude/CLAUDE.md)Team-shared, version-controlled
Local./CLAUDE.local.mdPersonal, gitignored

Loading is recursive upward from the directory you launch in — concatenated root-down, so "instructions closer to where you launched are read last" (last = loudest). Subdirectory files load on demand. Imports use @path syntax (e.g., @AGENTS.md for agent-file compatibility), nest up to four hops, and resolve relative to the importing file.

The craft (official best practices): target under 200 lines; add an instruction when Claude makes the same mistake a second time; be specific ("Run npm test before committing" beats "test your changes"); avoid contradictions — they make Claude pick arbitrarily; move multi-step procedures to skills; note that the project-root file is re-injected after /compact, surviving Lesson 0008's context churn. Bootstrap with /init; audit what actually loaded with /context.

Pillar 2: Permissions — where guarantees live

Permission rules name a tool and what it may do: Tool or Tool(specifier).

{ "permissions": {
    "allow": [ "Bash(npm run lint)", "Bash(npm run test *)" ],
    "deny":  [ "Read(./.env)", "Read(./.env.*)" ]
} }

Wildcards have teeth-geometry: put * after the subcommand (Bash(git log *), not Bash(git * main)); a trailing  * matches the bare command too — the space matters (Bash(ls *) skips lsof). Compound commands are matched per subcommand across separators like && and |.

The evaluation law: rules run deny, then ask, then allow — the first match determines the outcome. Consequences the exam probes:

  • A broad deny: Bash(aws *) beats a narrow allow: Bash(aws s3 ls) — "a deny rule can't carry allowlist exceptions."
  • An allow from one scope never outranks an ask from another.
  • A bare-tool deny (WebFetch) removes the tool from Claude's context entirely — Claude never even sees it.

Where rules live matters as much as what they say. Precedence for the same key: managed (org) > command line > project local > shared project > user — but permission lists merge across scopes rather than override. And there's trust gating: allow rules from a committed repo file apply only after each teammate trusts the folder, while deny and ask rules apply immediately. The "don't ask again" button writes an allow rule to .claude/settings.local.json.

Permission modes frame every session:

ModeBehavior
default (a.k.a. manual)Prompts on first use of each tool
acceptEditsAuto-accepts file edits + common filesystem commands (mkdir, mv…)
planRead-only exploration — see pillar 3
autoAuto-approves with background safety checks
dontAskAuto-DENIES anything not pre-approved — the name means "stop asking," and the answer is no
bypassPermissionsSkips prompts — "only in isolated environments like containers or VMs"; orgs can disable it

One more layer above rules: a PreToolUse hook with exit code 2 blocks a call before rules even evaluate — hooks beat rules. (Lesson 0006's confirmation gate, in its final form.)

Pillar 3: Plan mode — explore before you act

In plan mode, Claude reads files and runs read-only shell commands to explore, but doesn't edit your source files. Read-only forms (ls, cat, grep, read-only git) run unprompted; anything mutating goes through the normal permission flow. The architectural value: decisions about what to change get made with full context and zero risk — the same explore-first discipline this course's roadmap models before each lesson.

Exercise — configure the team repo (exam-style)

A five-person team wants, in their own words: (a) "nobody's Claude may ever read .env, company-wide"; (b) "lint and test should just run without prompting for everyone who joins the repo"; (c) "I keep getting prompted for npm run test" (one dev's complaint); (d) "new teammates shouldn't get auto-run powers the moment they clone"; (e) "Claude must never push directly to main — guaranteed."

On paper: for each item, name the exact file it belongs in, the rule or content to write, and — for (e) — which layer does the guaranteeing and why CLAUDE.md is the wrong answer.

Check your answer

(a) Managed (enterprise) settings — deny: ["Read(./.env)", "Read(./.env.*)"]. Org-wide, nothing overrides it, and deny rules need no trust gating.

(b) Committed .claude/settings.json — allow: ["Bash(npm run lint)", "Bash(npm run test *)"]. Shared with the repo.

(c) That dev should click "don't ask again" once — it writes the allow rule to their .claude/settings.local.json — or add the rule there by hand.

(d) Already handled: allow rules from committed files apply only after each teammate trusts the folder. Deny and ask would have applied immediately — the asymmetry is the feature.

(e) Not CLAUDE.md ("context, not enforced configuration"). The guarantee is a deny rule (e.g., Bash(git push origin main) and variants) or — strongest — a PreToolUse hook exiting 2, which blocks before rules even evaluate. If you noticed (e) is really 0006's confirmation gate question in work clothes, you're seeing the course's through-line.
