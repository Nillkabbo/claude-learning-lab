The flaky test hunt

In which a test fails only on Tuesdays, and you learn to be in two places at once.

≈ 10 minutes + hands-on Concepts: subagents · delegation · built-ins · tool grants Project gains: a reviewer subagent, a green-and-stable suite
Chapter 5 of 12 — the story so far.

The test that hated Tuesdays

It fails maybe one run in five. Never when you're watching. Priya's rule — releases abort on red — means your Fridays now contain a dice roll. "Flaky tests," says Marco, with the serene confidence of someone who has never fixed one, "are haunted."

Here's your actual problem, and the chapter's real subject: fixing the flake requires hunting — reading test history, checking for ordering, time, and randomness — and that hunt would flood your session with forty files of context you'll never need again. Meanwhile you have a real feature to finish.

Send a worker

You've met the built-ins by now — Explore (read-only, fast, thorough) and Plan (read-only context gathering). Today you use one without ceremony:

You: Use Explore to find why test_list intermittently fails. Suspect ordering or time dependence. Report back the cause and the two files involved — don't fix anything.

Explore churns through the test suite in its own context window. Your session stays clean; your feature keeps moving. Nine minutes later, a summary lands: the test sorts by timestamp, and two tasks created in the same second can arrive in either order. Deterministic fix: sort by id. You approve one small diff. Haunted house, exorcised.

The worker becomes permanent

But the deeper move — the one Priya actually wanted — is institutional. This week it's a flaky test; every week it's something worth investigating before touching. You formalize the pattern as a custom subagent, .claude/agents/detective.md:

---
name: detective
description: Investigates bugs and flaky tests read-only before any fix is
  attempted. Use proactively when a test fails intermittently or a bug's cause
  is unclear. Returns the suspected cause and the files involved.
tools: [Read, Grep, Glob]
---
You are a careful investigator. Find the smallest reproducible cause. Cite file
and line. Never edit — investigation only.

Three choices, each load-bearing: the description (delegation is description-driven — "use proactively" is what makes it volunteer); the tool list (Read, Grep, Glob — investigation can't edit, structurally); and the body, which is the agent's entire system prompt.

Next Tuesday, the test hiccups. Before you've finished reading the notification, the detective is already on it. Marco watches the session list. "It's like you have staff."

"I have one," you say. "Me. The rest are specialists."

What just happened, named Subagents = disposable context windows that return summaries. Built-ins (Explore, Plan, General-purpose) cover the common shapes; custom agents encode your team's recurring investigations. Delegation fires on the description — write it like a tool description: when, when-not, and "use proactively."

Your turn — the chapter's hands-on

Do it in your real repo
  1. Write a test that's genuinely flaky (e.g., iterating a set, or sorting same-second timestamps) — confirm it fails sometimes.
  2. Ask Explore (or Plan) to find the cause — no fixing. Read its summary.
  3. Apply the fix yourself; run the suite ten times; green every time.
  4. Create .claude/agents/detective.md (adapt the frontmatter above; description ≥ 2 sentences with "use proactively").
  5. In a fresh session, describe a vague problem and watch whether the detective volunteers — if it doesn't, sharpen the description until it does.

Checkpoint: stable suite (10/10 runs green), a committed detective agent that volunteers on vague bug reports. Report it — next chapter Tracker meets the outside world, and gets its first trust review.
