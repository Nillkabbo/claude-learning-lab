Lesson 0001 · Phase 1 — The API core

The anatomy of a Claude request

Claude remembers nothing. You remember everything. That's the whole lesson — the rest is detail.

≈ 10 minutes Exam: Prompt Engineering · Context Mgmt No coding needed

Every one of the five exam domains — agentic architecture (27%), Claude Code (20%), prompt engineering (20%), tools & MCP (18%), context management (15%) — quietly assumes one mental model: what a Claude API request actually is. Get this right and half the exam's "tricky" questions become obvious. Here it is.

The one idea: statelessness

The Messages API is stateless. Claude has no memory of any previous request. Not the last message, not the last conversation, not yesterday. If you ask a follow-up question, nothing — nothing — carries over unless you send it again.

That sounds like a limitation. It's actually the foundation of everything: because the model is stateless, your code owns the conversation. You decide what history exists, which turns are included, what gets summarized away, what gets retrieved from elsewhere. Context management (15% of the exam) is precisely the craft of managing that ownership well.

  STATELESS MODEL                          YOUR APPLICATION
  ┌───────────────┐   full history    ┌─────────────────────┐
  │               │ ◄───────────────  │  messages array     │
  │    Claude     │                  │  (you build this)   │
  │               │  ──────────────► │                     │
  └───────────────┘   one reply      └─────────────────────┘
        ▲                                   │
        └──────── nothing remembered ───────┘

Anatomy of a request

A minimal, complete request has three required parts and one you'll almost always set:

{
  "model": "claude-sonnet-4-5",
  "max_tokens": 1024,
  "system": "You are Tangerine Bank's assistant. Be concise.",
  "messages": [
    { "role": "user",      "content": "What's my checking balance?" },
    { "role": "assistant", "content": "Your checking balance is $412.50." },
    { "role": "user",      "content": "And my savings?" }
  ]
}
FieldRequired?What it is
modelYesWhich Claude handles this. Architects choose per task — capability vs cost vs latency.
max_tokensYesCap on response length. Required, and a classic exam trap: too small silently truncates output.
systemNoRole, rules, tone — the policy layer. Persists across the conversation you send.
messagesYesThe conversation: alternating user/assistant turns, oldest first. This array is the conversation.

Notice what the third user turn doesn't say: "my savings at Tangerine" or "you just told me my checking." It doesn't need to — the earlier turns are right there in the array. The model reads the whole thing fresh, every time.

Anatomy of the reply

{
  "content": [
    { "type": "text", "text": "Your savings balance is $8,230.00." }
  ],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 96, "output_tokens": 14 }
}

Three things your code will constantly branch on:

  • content is a list of blocks — not a plain string. A single reply can hold a text block and a tool-use block (Lesson 0005 builds on this).
  • stop_reason says why generation ended: end_turn (done), max_tokens (you truncated it), tool_use (it wants a tool called).
  • usage is your bill — inputs and outputs are priced differently, and the input grows as the conversation grows. That's the economic engine behind context management.
The win You can now diagnose the "amnesiac app": any chatbot that "forgets" earlier messages isn't haunted — its code is dropping turns from the messages array it resends. You know the fix, and you know why long chats get expensive (every turn re-bills the whole history as input tokens).
Common pitfall "Stateless API" ≠ "Claude has no memory features." Claude Code sessions, the Agent SDK, and memory tools all exist — but they are client-side machinery that manages and resends context for you. Underneath, every single call is still stateless. The exam rewards knowing which layer owns the memory.

Your turn

Exercise — the follow-up that failed

A colleague's banking bot breaks like this:

Turn 1 — user: "What's my checking balance?"
Turn 1 — bot:  "Your checking balance is $412.50."
Turn 2 — user: "Transfer $200 to savings from there."

The bot replies: "From where?". Its developer built turn 2's request containing only the turn-2 user message.

Fix it on paper: write the exact messages array the turn-2 request should contain (three entries, using the values above — the system prompt is "You are Tangerine Bank's assistant. Be concise.").

Check your answer 
"messages": [
  { "role": "user",      "content": "What's my checking balance?" },
  { "role": "assistant", "content": "Your checking balance is $412.50." },
  { "role": "user",      "content": "Transfer $200 to savings from there." }
]

Oldest first, roles alternating, the assistant's own reply included verbatim — that assistant turn is what lets "from there" resolve. If you also caught that the fix belongs in the code that builds the array (keep appending every turn), you're already thinking like an architect.
