System prompts & prefilling

Policy lives above the conversation — and one classic trick is now retired.

≈ 12 minutes Exam: Prompt Engineering · 20% No coding needed
Policy lives above the conversation; the task rides in user turns; a trailing assistant turn is a 400 on modern models.

Recall Lesson 0001: the API is stateless, so every request carries the whole conversation. There's one field that sits above the conversation — the system prompt. Today you'll learn what belongs there, how its power changed with newer models, and why the old "prefill the assistant's reply" trick now returns a hard error. That last one is exactly the kind of migration trade-off the architect exam loves.

The system prompt is policy, not conversation

A user message says: here is this task. The system prompt says: here is who you are and the rules for every task. Role, tone, scope, compliance rules, output format policy — standing decisions that shouldn't be re-litigated turn by turn. Even one sentence of role-setting measurably focuses behavior; Anthropic's own example is simply "You are a helpful coding assistant specializing in Python."

Belongs in the system promptBelongs in a user turn
Role and identity ("You are Tangerine Bank's assistant")The actual task or question
Standing tone and format policy ("Respond directly without preamble")Documents, data, and context for this turn
Compliance and safety boundaries ("never discuss competitors")Mid-conversation reminders and nudges
Tool-usage policy ("use parallel tool calls when independent")Per-turn exceptions to the defaults

Because the API is stateless, the system prompt is resent on every call — it's part of your input tokens every single time. That's fine for policy (it must never fall out of view), and it's also why per-task data does not belong there: it would ride along forever, billing tokens and diluting focus.

The 2026 twist — newer models over-respond Newer Opus models are more responsive to the system prompt than previous generations. Legacy "anti-laziness" idioms — CRITICAL: You MUST use this tool whenever… — were crutches for older models and now cause over-triggering (the model dutifully over-uses the thing you shouted about). The official fix: soften to plain phrasing — "Use this tool when…". Lesson for the exam: prompt idioms have model-version half-lives, and migrating prompts means dialing intensity back, not up.

Prefilling — the retired trick you must still recognize

Prefilling was a classic technique: end your messages array with a partial assistant turn, and the model would continue from it. Two famous uses:

  • Skip the preamble — prefill the assistant turn with a word or bracket so the reply starts mid-format.
  • Force a shape — prefill { so the answer has to be JSON.
// Legacy pattern — worked on earlier models
"messages": [
  { "role": "user",      "content": "Give me the account status JSON." },
  { "role": "assistant", "content": "{" }   ← the prefill: continue from here
]

On Claude 4.6 and later models (including Sonnet 5, Mythos 5, Fable 5) this is now a 400 error. Requests to those models must end with a user message. Earlier models still accept prefills, which is precisely why the exam includes them: real codebases still carry the pattern, and an architect must recognize it and know the migration paths.

Old prefill useModern replacement
Prefill a word to skip preambleSystem prompt: "Respond directly without preamble."
Prefill { to force JSONStructured outputs — schema-enforced (Lesson 0004)
Prefill reminders mid-conversationMove the reminder into the user turn (or hydrate via tools / context compaction)
The win You can now modernize a legacy integration on sight: spot the trailing assistant turn, know why it 400s on current models, soften the shouted system-prompt rules that old team wrote, and name the right replacement for each prefill use. That's a complete migration review — worth real exam points.
Scope note Adding assistant messages elsewhere in the conversation (real history from earlier turns) is unaffected — it's specifically the request ending with an assistant message that modern models reject as a prefill attempt.

Exercise — modernize the airline bot

A 2025-era integration hits two problems on a current model: a 400 error, and a status-summary tool firing on every message. Here's the whole request:

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "You are Apex Airlines' assistant. CRITICAL: You MUST ALWAYS call
             status_summary. You MUST NEVER add preamble. Output JSON only.",
  "messages": [
    { "role": "user", "content": "Rebook me on the morning flight." },
    { "role": "assistant", "content": "{" }
  ]
}

On paper: (1) explain the 400, (2) rewrite the system prompt so the tool rule won't over-trigger, (3) say where the "JSON only" requirement should go instead.

Check your answer

(1) The request ends with an assistant message — a prefill. Claude 4.6+ rejects that with a 400; requests must end with a user turn.

(2) Soften, don't shout: "You are Apex Airlines' assistant. Use status_summary when the passenger asks about a flight's status." Newer models are more responsive to system prompts, so the ALL-CAPS rule would keep firing the tool even for rebooking requests.

(3) "JSON only" is a format requirement with a shape — that's structured outputs territory (a schema), with "respond directly without preamble" in the system prompt for tone. If your rewrite kept JSON instructions in the system prompt and named structured outputs as the enforcement mechanism, full marks.
