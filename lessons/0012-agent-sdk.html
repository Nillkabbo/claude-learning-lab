Lesson 0012 · Phase 3 — Claude Code & the Agent SDK (final lesson of the phase)

Agent SDK: the loop as a library

Everything you've hand-built since Lesson 0005, handed to you as a function.

≈ 15 minutes Exam: Claude Code Configuration · 20% Code shown, none required
The product chooser: one axis — who runs the agent loop, and where.

Since 0005 you could build an agent by hand: send tools, read tool_use, execute, return tool_result, repeat. That's the Messages API contract — powerful, and yours to babysit. The Agent SDK's official tagline is the whole story: "Build production AI agents with Claude Code as a library" — the same tools, agent loop, and context management that power Claude Code, running in your process.

The product chooser (a complete exam answer)

ProductWho runs the agent loopYou reach for it when
Messages API / Client SDKYou — you implement the tool loop yourselfYou want full control: custom loops, 0004-style structured outputs, minimal machinery
Agent SDK (Python / TypeScript)The library — in your processYou want the Claude Code engine (tools, context management, skills) embedded in your app
Claude Code CLIBuilt-in — interactive terminal harnessHuman-driven, one-off or team work in a repo
Managed AgentsAnthropic — hosted REST, sandbox includedYou don't want to run anything at all

Two footnotes worth exam points: the Agent SDK exists for Python and TypeScript only — for other languages, the official pattern is running the CLI as a subprocess with -p and --output-format json. And the axis the table really encodes is one question: who runs the loop, and where?

query(): the one function

# Python
async for message in query(
    prompt="Review utils.py for bugs. Fix any issues you find.",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Edit", "Glob"],
        permission_mode="acceptEdits",
    ),
):
    ...
// TypeScript
for await (const message of query({
  prompt: "...",
  options: {
    allowedTools: ["Read", "Edit", "Glob"],
    permissionMode: "acceptEdits"
  }
})) { ... }

You iterate messages: assistant messages carrying content blocks (text reasoning, or a tool name being executed — the loop from 0005 running inside), and a final ResultMessage. The progression the docs teach is the allowlist widening: read-only (Read, Glob, Grep) → code modification (+ Edit) → full automation (+ Bash). Other options: system_prompt (0002's craft), mcpServers, and more.

Guardrails in code

  • permission_mode — 0009's modes, set programmatically ("acceptEdits", "plan", …).
  • allowedTools — the allowlist as first-class option; 0011's minimal-tool-grant discipline, now in your constructor.
  • canUseTool — a programmatic approval callback: your code decides per call. This is 0006's confirmation gate and 0009's permission prompt merged into one function you own.
  • Hooks — 0010's lifecycle events, runnable from the SDK too.

Sessions, and the traveling team config

Sessions "maintain context across exchanges, resume or fork later" — 0008's multisession pattern and 0011's fork, productized. And the config your team built travels with it: skills, commands, and memory load automatically from your project's .claude/ and ~/.claude/ — "same as Claude Code." The artifact map from 0010 isn't CLI-only; it's the SDK's configuration surface. Subagents spawn, MCP servers connect, plugins package the lot.

The win — Phase 3 complete You can now choose the right product for any scenario (the four-way table), wire an Agent SDK invocation with scoped tools and permission modes, place the confirmation gate in code via canUseTool, and know that your team's .claude/ artifacts ride along. Exercise — pick the product (exam-style)

Four Apex projects, four teams: (a) a nightly unattended batch that fixes doc-comment errors across 200 repos, running in containers; (b) an interactive copilot for support engineers that reads tickets and drafts replies — but any file write needs a human click; (c) a Go microservice that triages bug reports into categories; (d) a one-shot extractor pulling a policy number from an email body into JSON.

On paper: pick the product for each — Messages API, Agent SDK, CLI, or Managed Agents — and for the Agent SDK cases, sketch the options (system prompt, allowed tools, permission mode, and where the approval gate lives).

Check your answer

(a) Agent SDK (TS or Python), headless in the container: system_prompt scoped to doc fixes, allowed_tools: ["Read", "Edit", "Glob", "Grep"] — notably no Bash — permission_mode: "acceptEdits". Unattended + isolated container is the one habitat where permissive modes are defensible.

(b) Agent SDK with the approval in code: allowed_tools including writes, but the human click lives in canUseTool — your callback returns allow only after approval. The confirmation gate as a function.

(c) CLI as subprocess with -p --output-format json — the official pattern for languages without an SDK. (Managed Agents is defensible if they'd rather not run it; the reasoning is the point.)

(d) Messages API + structured outputs (0004) — one schema, one call, zero agent machinery. If you flinched at using an SDK here, your instincts are exam-ready.
