The subagent contract

A subagent is a specialized assistant that "runs in its own context window with a custom system prompt, specific tool access, and independent permissions." When a side task would bury your conversation in logs, search results, and file contents, the subagent does that work separately and "returns only the summary."

  MAIN CONTEXT (clean, small, expensive-to-lose)
      │  "audit auth for CVE-2026-1234"
      ├──────────► [Explore subagent] ── 300 pages of grep noise
      ├──────────► [reviewer subagent] ── 40 files read
      └──────────► [reviewer subagent] ── ...
                          │
      ◄────── three summaries, synthesized ──────┘
  (workers' contexts are disposable; yours isn't)

Building one

A subagent is a Markdown file — frontmatter plus a body that becomes its system prompt (0002's craft, applied to a worker):

---
name: code-reviewer
description: Reviews diffs for security and style. Use proactively
  after any multi-file change. Use for pull request feedback.
tools: [Read, Grep, Glob, Bash]
model: sonnet
---
You are a senior reviewer for Apex Airlines tooling. Flag: secrets in
code, missing error handling, permission-relevant changes...        ← body = system prompt
  • Required frontmatter: name (lowercase-hyphens) and description — the delegation trigger. Phrases like "use proactively" encourage proactive delegation. This is 0006's four-question discipline again: when, when-not, scope, limits.
  • Optional powers: tools (allowlist; inherits all if omitted), model (defaults to inherit), permissionMode, maxTurns, skills (preloaded), memory, isolation: worktree, background.
  • Scopes and priority: managed settings > --agents CLI flag (session-only) > .claude/agents/ (project, committed) > ~/.claude/agents/ (user) > plugin directories. Edits hot-reload within seconds — no restart.

Delegation mechanics

Delegation is description-driven: Claude combines each subagent's description with your request and current context. A vague description is a subagent that never gets called — or gets called wrongly. You can also invoke explicitly (natural language, @-mention, or run a whole session as one via claude --agent <name>).

What a fresh (non-fork) subagent starts with: its own system prompt + environment details (not the full Claude Code prompt), the task message Claude writes for it, the CLAUDE.md hierarchy and a git status snapshot (the built-in Explore and Plan agents skip both), preloaded skills, and a sibling-agent roster. Nothing else — no parent conversation.

The fork exception A fork (0010's context: fork, or /subtask) inherits the entire conversation — prompt cache included — making it cheaper for tasks that need the same context. Either way, the worker's tool calls stay out of your transcript; only the final result returns.

Parallelism & the built-ins

  • Parallel spawns for independent work, with Claude synthesizing the findings — the orchestrator-workers pattern, arriving in force in Phase 4. Background subagents run while you keep working (their permission prompts surface in your session).
  • Default limits: 20 concurrent subagents, nesting 3 layers deep (both adjustable via environment variables — good trivia, better architecture constraints).
  • Built-ins: Explore (read-only, thoroughness levels, model capped at Opus), Plan (read-only context gathering), General-purpose (all tools, multi-step exploration + action). Built-ins inherit parent permissions; custom subagents override with permissionMode.
  • Subagents are resumable via SendMessage, retaining their history.

The three-artifact division of labor

ArtifactAnswersForm
CLAUDE.mdWhat's true here — standing facts, conventionsMarkdown, <200 lines, every session
SkillHow we do X — procedures, with supporting filesSKILL.md + files; invoked or auto-loaded on relevance
SubagentWho does X — an isolated worker with its own prompt, tools, permissions.claude/agents/*.md, delegated by description
The win You can now design a worker fleet: focused subagents with complete delegation descriptions and minimal tool grants, skills carrying the procedures they preload, forks where shared context pays, parallel spawns where independence pays — and a clean main context as the organizing principle behind all of it.

Exercise — design the release fleet

The Apex tooling team ships weekly. They want: (a) a release-notes drafter that reads commits and PRs — read-only, and it should volunteer itself after merges; (b) a migration runner that may edit files but must never run arbitrary shell commands; (c) a reusable "how we tag releases" procedure with a reference table teammates keep updating; (d) a weekly audit where three reviewers work in parallel and one summary comes back.

On paper: for each, choose the artifact (subagent / skill / both), give the file path, and write the delegation description or frontmatter — including tool lists.

Check your answer

(a) Subagent: .claude/agents/release-notes.md, tools: [Read, Grep, Glob], description: "Drafts release notes from commits and merged PRs. Use proactively after merges to main." (The "use proactively" phrase is the official lever for volunteering.)

(b) Subagent: tools: [Read, Edit, Grep, Glob] — the point is the omission of Bash: the allowlist is the security boundary, and inherited permissions still gate what remains.

(c) Skill: .claude/skills/release-tagging/SKILL.md with the reference table as a supporting file (skills' whole advantage over commands). Optionally preload it into the release subagents via frontmatter skills:.

(d) Three parallel subagent spawns — e.g., three reviewers with focused scopes (security, perf, docs) — with the main agent synthesizing. Within defaults: 3 ≪ 20 concurrent, depth 1 ≪ 3. If you also said "each gets a fresh context, so the audit costs nothing in main-context rot" — that's the architect's answer.
