Composition patterns: the workflow cookbook

Chaining, routing, parallelization, evaluator-optimizer — four ways your code owns the flow.

Pattern 1: Prompt chaining

  task ──► [LLM 1] ──► gate ──► [LLM 2] ──► gate ──► ... ──► result
             step           check            check

Decompose the task into a fixed sequence; each call does one focused thing. The craft is in the gates — "programmatic checks… between steps to ensure that intermediate results are on spec" before the chain continues. That's Lesson 0004 doing assembly-line duty: gate = schema-validate the intermediate output, check what the grammar can't (semantic rules), and stop or re-run when a step fails spec.

  • Use when: the task decomposes cleanly into fixed subtasks; you're trading latency for accuracy; each step benefits from a smaller, focused prompt.
  • Known win: it "works better for inducing context" — e.g. generate a document, then generate its title with the document in context; or generate few-shot examples, then run the real task with them.
  • When-not: steps can't be fixed in advance (that's 0015, or an agent); a single call already meets spec.

Pattern 2: Routing

            ┌──► [easy tier: Haiku handler]        cheaper
  input ─► classifier ──► [hard tier: Sonnet handler]     stronger
            └──► [sensitive tier: certified model only]   compliant

Classify the input, dispatch to a specialized handler with its own prompt. Three distinct wins — the exam likes all three named:

  • Focus: separate prompts per category — "cleaner prompts," isolated concerns, less cross-category bias.
  • Cost: tiered models — Haiku for easy inputs, Sonnet for harder ones.
  • Privacy: enforce where data may go — sensitive inputs routed only to approved, certified models. Routing as a policy enforcement point.

Implementation: the classifier is a structured-output call (0004) over a fixed label set — enums close the world; the router is your code, not the model's judgment. Use when "a complex task has distinct categories that are better handled separately"; when-not: when categories blur and misroutes dominate.

Pattern 3: Parallelization

  SECTIONING (split work)          VOTING (same work, N lenses)
  task ─┬► [LLM A] ─┐              task ─┬► [LLM 1: flag issues] ─┐
        ├► [LLM B] ─┼► merge              ├► [LLM 2: flag issues] ─┼► threshold
        └► [LLM C] ─┘                     └► [LLM 3: flag issues] ─┘

Two flavors: sectioning — independent subtasks run concurrently and merge; voting — the same task runs multiple times, with a threshold deciding. Use for speed (parallel subtasks), or when "you need multiple perspectives and high success rate on the first try." Two canonical examples:

  • Guardrails: one instance answers the user while another screens the same content for harm concurrently — latency of safety ≈ zero.
  • Vulnerability review: "multiple prompts flagging different issues, with a threshold to balance false positives and negatives." The threshold is a business decision (precision vs recall), and you own it.

Don't confuse this with 0005's parallel tool calls (one model, one turn) or 0011's parallel subagents (workers in an agent harness) — though the sectioning idea unifies them all.

Pattern 4: Evaluator-optimizer

  task ──► [generator LLM] ──draft──► [evaluator LLM] ──feedback──┐
     ▲                                                            │
     └────────────────── loop ◄───────────────────────────────────┘

One call generates; another "provides evaluation and feedback in a loop." The essay's analogy: "a clear-eyed human with specialized knowledge… going back and forth with a gifted writer iterating on a rough draft." Examples: literary translation with a bilingual critic; web research needing multiple rounds.

  • Use when: clear evaluation criteria exist and iterative refinement demonstrably improves results — both conditions, or it's just paying twice.
  • When-not: "when a clear LLM judge can't be formulated" or judgment criteria are unfalsifiable vibes. No judge, no loop.

Patterns compose

"These building blocks aren't prescriptive" The essay's closing word on patterns: they "aren't prescriptive… successful implementations will often be customized and combined." Route first, then chain within a route; vote on sensitive steps, chain the rest; add complexity "only when it demonstrably improves outcomes" — the same rule as the ladder.
The win Four patterns, each with shape, use-when, when-not, and implementation hooks — plus the license to compose them. Roughly half of the 27% domain's scenario questions are one of these four wearing a business costume.

Check your answer

Route first: a structured-output classifier over {easy, hard, regulated, abusive}. Easy → Haiku handler (cost tiering). Hard → Sonnet handler (capability tiering). Regulated → certified-model handler only (privacy enforcement). Abusive → canned safe response.

Chain inside the answer routes: retrieve docs → draft with citations → gate (schema: citations present? claim-span grounding? — programmatic, 0004) → emit. Easy tier may skip the polishing chain.

Vote on safety: three screeners over the draft, threshold 2/3 — an explicit precision/recall decision. Runs concurrent with drafting, so safety adds ~zero latency (the essay's guardrails arrangement).

Evaluator-optimizer for premium only: draft → critic (clarity, citation fit) → revise loop, capped — clear criteria, demonstrable value, contained latency. If your sketch routed before everything else and gated between every step, you've internalized why order matters: policy outermost, quality innermost.
