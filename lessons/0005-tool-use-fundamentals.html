Tool use fundamentals: the loop

Phase 1 gave Claude a guaranteed voice. Tools give it hands.

≈ 14 minutes Exam: Tool Design & MCP · 18% No coding needed

Welcome to Phase 2 — the 18% of the exam where "Tool Design & MCP" lives, and the foundation of the 27% agentic-architecture domain after it. Everything today builds on two Phase-1 facts: responses are lists of typed content blocks (0001) and requests must end with a user message (0002). By the end you'll see why both are true because of tools.

The loop

Lesson 0005 — the tool loop: the model requests, you execute, results ride back in a user message — until end_turn.

Step by step:

  1. You send a request whose tools array defines each tool's name, description, and input_schema (a JSON Schema — the same shape Lesson 0004 taught you to reason about).
  2. Claude replies with stop_reason: "tool_use" and one or more tool_use content blocks — each with a unique id, the tool name, and structured input.
  3. Your code executes the operation. Claude never runs your tools; it requests them.
  4. You send the next request with the conversation extended: the user message, the assistant's full previous turn (including the tool_use blocks), and a user message containing a tool_result block matched by tool_use_id.
  5. Claude replies with the final answer, citing the result you supplied.
// Step 4's messages array — the shape that makes or breaks the loop
"messages": [
  { "role": "user", "content": "What's the weather in Austin?" },
  { "role": "assistant", "content": [
      { "type": "tool_use", "id": "toolu_01A", "name": "get_weather",
        "input": { "location": "Austin, TX" } }
  ]},
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01A",
        "content": "34 degrees Celsius, sunny" }
  ]}
]

Now two Phase-1 facts click into place. The tool_result rides in a user message — that's why requests end with one. And because the API is stateless, the assistant's tool_use turn must be echoed back in full: Claude doesn't "remember" requesting the tool; it re-reads the transcript you send. (Notice also: without content blocks being a typed list, a reply couldn't contain text and a tool call at once.)

Steering the decision: tool_choice

tool_choiceEffectArchitect's use
auto (default)Claude decides per turn: call a tool or answer directlyThe normal case — judgment stays with the model
anySome tool must be calledForce action when plain text would be wrong
toolA specific named tool must be calledGuaranteed invocation — no prompting reliance
noneNo tools this requestCosts zero extra system-prompt tokens when no tools are sent

auto also takes disable_parallel_tool_use: true when you want at most one call per turn — because by default, a response may contain multiple tool_use blocks (parallel tool calls). Handle each one, and return one tool_result per tool_use_id.

When should you force a tool vs use structured outputs? Forcing a tool was the classic extraction trick, and strict: true on the definition now guarantees the call's schema — but when the deliverable is data, Lesson 0004's output_config.format is the cleaner tool. Reach for forced tools when the deliverable is an action the model must take.

Scope note — the tool ecosystem Everything above is client tools: your code executes them. The API also has server tools (web_search, web_fetch, code_execution) that run on Anthropic's infrastructure — you see results without executing anything. SDKs add a Tool Runner that executes your tools automatically, and an MCP connector for remote tool servers. All of these reuse the same loop; they just move who runs step 3. MCP gets its own lesson later in this phase.

The bill, and a model-behavior nuance

  • Tools cost tokens on every request: the tools definitions themselves, the tool_use/tool_result blocks, plus an automatic tool-use system prompt — roughly 264–804 tokens depending on model and tool_choice. Every tool you add bills every request, whether used or not. That's the economic pressure behind keeping tool sets small and descriptions tight.
  • Missing required parameters behave differently by model: Opus tends to ask for them; Sonnet may infer a plausible value. Design schemas so that neither behavior breaks you — unambiguous descriptions, and required truly meaning required.
The win You can trace and hand-write the entire loop: read a tool_use response, execute, and construct the follow-up messages array correctly — including the two mistakes everyone makes (dropping the assistant turn, losing the tool_use_id). That trace is the atom from which every agentic pattern in Phase 4 is built.

Exercise — repair the broken loop

A junior dev's weather bot dies after step 2. The API rejects their follow-up request. Here's what they sent as the complete messages array:

"messages": [
  { "role": "user", "content": "What's the weather in Austin?" },
  { "role": "user", "content": [
      { "type": "tool_result", "content": "34 degrees, sunny" }
  ]}
]

The original response's tool_use block was:

{ "type": "tool_use", "id": "toolu_01A", "name": "get_weather",
  "input": { "location": "Austin, TX" } }

On paper: (1) name both mistakes, (2) write the corrected messages array.

Check your answer

(1) Mistake one: the assistant's tool_use turn is missing — the transcript jumps from user to user, and the request ends with history the model can't reconcile (and on modern models a trailing oddity like this reads as a malformed prefill attempt). Mistake two: the tool_result has no tool_use_id, so nothing links the result to the request that produced it.

(2)

"messages": [
  { "role": "user", "content": "What's the weather in Austin?" },
  { "role": "assistant", "content": [
      { "type": "tool_use", "id": "toolu_01A", "name": "get_weather",
        "input": { "location": "Austin, TX" } }
  ]},
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "toolu_01A",
        "content": "34 degrees, sunny" }
  ]}
]

If you got both without peeking, you've internalized the loop — and you can now debug roughly half of all real-world tool-integration bugs on sight.
