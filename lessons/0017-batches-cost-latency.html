Message Batches: 50% off anything patient

  • Pricing: "All usage is charged at 50% of the standard API prices" — and it stacks with prompt caching.
  • Timing: most batches finish in under an hour; the hard ceiling is 24 hours (expired work isn't billed). Results stay downloadable for 29 days.
  • Size: 100,000 requests or 256 MB per batch, whichever comes first.
  • Mechanics: submit a requests array where each entry carries a unique custom_id; poll until ended; fetch one .jsonl file. Results may not match input order — the custom_id is your join key.
  • Failure model: not all-or-nothing — one failed request doesn't affect the rest, and errored/canceled/expired requests are unbilled.
  • Constraints: no streaming; max_tokens must be ≥ 1 (the 0-token cache pre-warm trick doesn't apply); separate rate limits from the Messages API.
  • Use for: exactly the workloads 0016 created — large-scale evaluations — plus moderation sweeps, bulk analysis, bulk generation. Anything where "immediate responses are not required."

Prompt caching: repetition at 0.1×

The craft rules

Lesson 0017 — the cache invalidation hierarchy: tools → system → messages.
:

  • Static first, dynamic last — cached content at the prompt's beginning; put the breakpoint on the last block that stays identical across requests (never on the timestamp or the incoming user message).
  • Up to 4 breakpoints, ordered by change frequency (and automatic caching consumes one slot). Minimum cacheable size varies by model — 512 to 4,096 tokens; shorter prompts just process uncached, no error.
  • TTL: 5 minutes by default, refreshed free each use — the clock includes response generation time. The 1-hour TTL costs double on writes; when mixing, 1-hour breakpoints must come before 5-minute ones.
  • The invalidation hierarchy — memorize this: tools → system → messages. A change at any level invalidates that level and everything after it. Change a tool definition: all three die. Toggle tool_choice or swap an image: messages only. This one hierarchy explains 0004's "changing the format invalidates your prompt cache" and 0008's clear_at_least (clearing tool results rewrites messages — don't torch the cache for a small save).

The arithmetic, worked once

Nightly eval suite — 80,000 requests, stable 2,000-token system + tools Naive synchronous: 80,000 × base input price.
Batched: × 0.5.
Batched + cached prefix: the 2,000-token stable prefix reads at × 0.1 (after the first write at 1.25×), stacked with the batch discount.
Shape of the win: half off for patience, 90% off the repeated part for stability — and they multiply. Interactive work keeps only the caching lever; latency-bound work keeps neither and pays full freight for speed.
The win You can now read any bill and pick levers: batch the patient work, cache the stable prefixes (static-first, breakpoint on the last stable block, 4 slots by change frequency), size thinking/effort to the task, keep tool sets lean, and route tiers. Cost engineering as a design activity, not a panic.

Your turn

Exercise — engineer three bills (exam-style)

(a) Nightly 80K-document classification eval with a stable rubric and tool set. (b) An interactive tutor: 3,000-token curriculum that never changes, then a growing conversation. (c) A team that redeploys its tool definitions every Tuesday.

On paper: for each — batch or not; the cache design (breakpoint placement, TTL choice); the multiplier arithmetic shape; and the one trap to avoid.

Check your answer

(a) Batch, ×0.5. Cache the stable rubric+tools prefix: first request writes (1.25×), the rest read (0.1×) — stacked. Trap: leaving a timestamp in the system prompt, which mutates the "stable" prefix every run and kills the cache at the hierarchy's top.

(b) No batch — latency is the product. Static-first: tools → curriculum → breakpoint → conversation. Each turn's history is the growing prefix: earlier turns read at 0.1×, only the new suffix pays full price. 5-minute TTL refreshes free while the session is active; 1-hour TTL only for sparse-return users, budgeted against the 2× write. Trap: images or tool_choice churn mid-conversation invalidating messages.

(c) Weekly tool changes invalidate everything (top of the hierarchy) — so don't build the business case on cache savings crossing Tuesday deploys; schedule tool releases, keep descriptions stable in between (0010's name/description nuance in the grammar cache is the same instinct), and expect the first post-deploy request to eat the write premium. If your answer quantified (c) as "one full-price + write-premium day per week, cached reads the rest," you're doing architect arithmetic.
