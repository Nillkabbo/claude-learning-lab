Error handling in agent tools

Errors aren't exceptions here — they're messages the model reads to decide what happens next.

≈ 14 minutes Exam: Tool Design & MCP · 18% No coding needed

In ordinary code, errors are for programmers — stack traces, log lines, nobody's decision. In the tool loop, an error becomes part of the conversation: Claude reads it and chooses the next move. That makes error design a branch of prompt design — and the exam's "error handling in agent tools" area is exactly this judgment. Three things to master: the mechanics of signaling, the classification that drives behavior, and the state you can't see.

Signal with is_error, never exceptions

Don't raise exceptions through the API. Return the failure in the channel the model reads — a tool_result with is_error: true:

{ "role": "user", "content": [
  { "type": "tool_result",
    "tool_use_id": "toolu_01A09q90",
    "content": "ConnectionError: the weather service API is not available (HTTP 500)",
    "is_error": true }
]}

Claude incorporates the error into its response — telling the user, suggesting a retry later, or routing around the failure. Two adjacent behaviors worth knowing:

  • Invalid tool calls self-correct: if Claude requests a tool with bad or missing parameters, it typically retries 2–3 times with corrections before apologizing — and you can help it along with errors like "Error: Missing required 'location' parameter".
  • Or don't have the problem at all: strict: true on the definition guarantees schema-valid inputs (Lesson 0004), eliminating invalid calls at the source.

The classification that drives behavior

The official principle: "write instructive error messages" — what went wrong and what to try next. The classification underneath:

ClassExamplesThe message should
Transient (retryable)Rate limit, HTTP 5xx, read timeoutSay it's retryable and give parameters: "Rate limit exceeded. Retry after 60 seconds."
Permanent (adapt)Invalid input, not found, forbiddenPoint to the alternative: "No such airport code; use search_airports first"
Uncertain (verify)Timeout after a side effect may have firedSay the outcome is unknown: see below — this is the architect's trap

A transient error without retry guidance invites the model to guess (hammer the API or give up). A permanent error phrased as "failed, try again" invites pointless retries. The message text is the control logic.

The trap: uncertain state

Where real money gets lost Your payment tool times out. Did the charge fire? You don't know. If the error says "failed, retry," the model retries — and double-charges. The correct result: "Request timed out after submission; charge status UNKNOWN. Do not retry — verify with get_charge_status before any retry or rebooking." The error must distinguish failed cleanly from state unknown.

The stronger fix is structural: idempotency keys. If the payment accepts a client-generated key and charges at most once per key, then "retry" becomes safe by construction and your error messages can be simpler. When the exam asks how to make retries safe against side effects, that's the answer.

Formatting rules that 400

  • tool_result blocks must immediately follow their corresponding tool_use blocks in history.
  • Inside the user message, tool_result blocks come first — any accompanying text goes after them.
  • The tell-tale API error when you get this wrong: "tool_use ids were found without tool_result blocks immediately after" — that's ordering, not content.

MCP's two-lane error system

MCP formalizes the split you've been improvising:

  • Protocol errors — standard JSON-RPC errors: unknown tool, invalid arguments. These are communication failures; they don't reach the model as recoverable content.
  • Tool execution errors — the tool ran but failed: reported in-band with isError: true inside a successful response, deliberately routed so the LLM can see and recover from them.

The classic implementation bug (a real pattern in the wild): returning execution errors as protocol errors — which hides them from the model and kills its ability to adapt. And note the corollary: an MCP call can return HTTP 200 and still have failed; a single status check never covers both lanes.

Security note Tool results often carry untrusted external content — fetched pages, emails, uploads. Keep that content inside tool_result blocks, not in system prompts or plain user text. It's the containment boundary against indirect prompt injection, and it returns with machinery in Phase 3.
The win You can now design a complete error surface: is_error signaling with instructive text, the transient/permanent/uncertain classification driving model behavior, idempotency making retries safe by construction, correct ordering, and the MCP protocol-vs-execution mapping. That's the full "error handling in agent tools" exam area, end to end.

Your turn

Exercise — classify and write four failures

Apex Airlines' agent hits four failures in one hour. For each, classify it (transient / permanent / uncertain / protocol error) and write the exact tool_result content you'd return:

  1. search_flights returns HTTP 429 with header Retry-After: 30.
  2. get_weather is called with "AUST" — not a valid IATA code.
  3. charge_card times out after submission; status unknown.
  4. The orchestrator calls flight_search — a tool name that doesn't exist on the MCP server.
Check your answer
  1. Transient. "Rate limit exceeded. Retry after 30 seconds." — reuse the server's own retry parameter.
  2. Permanent. "Invalid IATA airport code 'AUST'. Use exactly three letters (e.g., AUS). Call search_airports if unsure of the code." — the alternative path is named, so the model adapts instead of guessing again.
  3. Uncertain. "Timed out after submission; charge status UNKNOWN. Do not retry. Verify with get_charge_status before rebooking." — and the structural fix is an idempotency key so future retries are safe by construction.
  4. Protocol error. This never becomes a tool_result at all — the MCP server answers with a JSON-RPC error (unknown tool). It's a communication failure; if you found yourself "writing content" for it, revisit the two lanes.

Four for four? You've got the judgment this exam area tests — the same classification, applied under different costumes.
