Lesson 0006 · Phase 2 — Tools & context

Designing tool interfaces models use correctly

A tool definition is UX for a non-human user — and the description is the interface.

≈ 14 minutes Exam: Tool Design & MCP · 18% No coding needed
The tool interface is a card the model reads — and the description is by far the most important factor.

Lesson 0005 taught the loop's mechanics. Today is the craft: why does Claude use one tool flawlessly and fumble another? The model chooses tools by reading — name, description, schema. That readable surface is a user interface, and you are its designer. The official docs are blunt about where the leverage is: "Provide extremely detailed descriptions. This is by far the most important factor in tool performance."

The description is the interface

A working description answers four questions. Aim for at least 3–4 sentences, more for complex tools:

  1. What it does — precisely, including units and formats of what it returns.
  2. When to use it — and when not to. The negative space prevents mis-selection.
  3. What each parameter means and how it changes behavior.
  4. Caveats and limitations — what the tool does not return or do.
Poor (leaves Claude guessing)Good (answers all four)
"Gets the stock price for a ticker."

One line. No parameter meaning, no scope, no boundaries — "many open questions about the tool's behavior and usage."		 Gets the latest trade price for a publicly traded company on a major US stock exchange. Input must be a valid ticker symbol. Use when the user asks about the current or most recent price. Returns the price in USD only — it will not provide any other information about the stock or company.

Notice the good version spends its sentences on decision support: validity, scope, currency, and the explicit "will not." A model that knows what a tool doesn't do stops reaching for it when it shouldn't — that's mis-selection engineering.

Naming and consolidation

  • Namespace meaningfully: github_list_prs, slack_send_message — service prefix plus plain verb. This matters especially when tool search is involved, and names must match ^[a-zA-Z0-9_-]{1,64}$.
  • Consolidate related operations. Not create_pr + review_pr + merge_pr, but one tool with an action parameter. Official reasoning: "fewer, more capable tools reduce selection ambiguity" — and each avoided definition also cuts the 264–804-token overhead from Lesson 0005.
The trade-off exam candidates miss Consolidation has a failure mode: the mega-tool whose action enum hides a second schema ("for action X these params matter, for Y those"). The cure is the four-question description applied per action, and enums kept honest. Sprawl and mega-tools are the two ends of the same bad axis; the sweet spot is few tools, each with a complete interface.

Schemas that decide

  • Every parameter gets a description with format hints: "City and state, e.g. San Francisco, CA". Remember Lesson 0005's nuance — Opus asks when a param is ambiguous, Sonnet may infer. Descriptions that remove ambiguity protect you from both.
  • Close open worlds with enums — "enum": ["celsius", "fahrenheit"] — and still describe what the values mean. This is Lesson 0004's enum support doing double duty inside tool schemas, with strict: true guaranteeing the call's shape.
  • input_examples for complex tools — nested objects, optional parameters, format-sensitive inputs. Two rules: each example must validate against the input_schema (invalid ones → 400 error), and they work on client tools, not server tools. Cost: ~20–50 tokens per simple example, 100–200 for nested ones — another place description quality comes first, examples second.

Results are context

The loop's step 3 is yours, and so is its output shape. Official guidance: "design tool responses to return only high-signal information."

  • Return semantic, stable IDs (slugs, UUIDs), not opaque internal references.
  • Include only the fields Claude needs next — not the raw API dump.
  • "Bloated responses waste context" — and worse: by Lesson 0001's statelessness, every token in a tool_result is re-billed as input on every subsequent turn of that conversation. Chatty tools are a permanent tax, not a one-time cost.
Design principle — the confirmation gate Irreversible or external-side-effect actions (booking, sending, paying, deleting) need a confirmation gate in your execution loop — step 3 of Lesson 0005's diagram is your code, so human-in-the-loop approval lives there, not in the model's goodwill. This principle returns with real machinery in Phase 3 as Claude Code's permission system.
The win You can now do a senior-review audit of any tool definition on six axes: description completeness (the four questions), naming, consolidation balance, enum closure, result signal-to-weight, and confirmation gating for irreversible actions. That checklist maps almost one-to-one onto the exam's tool-design questions.

Exercise — audit the booking tool

A teammate ships this tool and complains "Claude keeps misusing it":

{
  "name": "flight",
  "description": "Books a flight.",
  "input_schema": {
    "type": "object",
    "properties": {
      "from": { "type": "string" },
      "to":   { "type": "string" },
      "cabin": { "type": "string",
                 "description": "The cabin." }
    },
    "required": ["from", "to", "cabin"]
  }
}

Execution returns the airline GDS's raw 4,000-token response. It also charges the corporate card immediately.

On paper: (1) audit it against the six axes from this lesson; (2) rewrite the description with all four questions answered; (3) fix the cabin parameter; (4) specify the result shape and where the confirmation gate belongs.

Check your answer

(1) Audit: description fails all four questions (no when/when-not, no parameter meanings, no limitations — "Books a flight" answers nothing a chooser needs); name isn't namespaced or verb-like; cabin is an open string where the world is closed; the 4,000-token raw result violates high-signal design; and an immediate charge with no gate is the confirmation failure.

(2) Model answer — "Books a revenue flight on Apex Airlines' inventory and immediately charges the corporate card. Use when the user has explicitly confirmed a specific itinerary. Do not use for fare search or holds — use search_flights. Inputs are IATA airport codes (e.g., AUS, JFK), not city names. Returns only the booking reference and final price; it does not return seat assignments."

(3) "cabin": { "type": "string", "enum": ["economy", "premium_economy", "business", "first"], "description": "Cabin class; premium_economy is not offered on regional jets." } — closed world, described values.

(4) Return { booking_ref, price_usd, cabin } — semantic, next-step-sized. The confirmation gate belongs in your execution code (step 3 of the loop): require explicit user confirmation before charging, regardless of what the model decides. If your audit caught that the model can't be trusted to be the gatekeeper — only the interface — you've got the architect's instinct this domain tests.
