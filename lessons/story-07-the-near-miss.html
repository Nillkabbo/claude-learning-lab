The near-miss

In which nobody deletes the tasks file, and that non-event is the whole chapter.

≈ 10 minutes + hands-on Concepts: permission rules · hooks · enforcement layers Project gains: guardrails that fail safe

5:58 p.m.

Marco is cleaning up a scratch directory. His session, trying to be helpful, proposes: rm -rf . — from inside tracker/. He clicks approve. The terminal doesn't move.

Because at 5:58 p.m., nothing happens. That — the non-event — is this chapter. Something you built earlier this afternoon refused the command.

From note to law

Rewind to lunch. Your CLAUDE.md has said "Do not commit tasks.json" since Chapter 3, and this morning it finally happened anyway — Claude, mid-refactor, helpfully staged everything. The note was guidance, and guidance can be forgotten. You'd remembered the law from your own notes: memory is context, not enforcement. So you spent lunch making it law, in two layers:

Layer one — permission rules. In .claude/settings.json, committed for the whole team:

{ "permissions": {
    "allow": ["Bash(python *)", "Bash(git status)", "Bash(git diff *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Bash(rm -rf *)", "Bash(git push * main)", "Read(./tasks.json)"]
} }

Evaluated in a strict order you now know by heart: deny, then ask, then allow — first match wins. A broad deny can't be rescued by a narrow allow. Pushes to main simply cannot happen. And when Marco's fresh clone pulls the repo, the allow rules wait until he trusts the folder — while deny rules apply the instant the settings load. New machines are safe on arrival.

Layer two — a hook. Rules say what's forbidden; hooks react to what's happening. A ten-line PreToolUse script logs every Bash command to .audit.log and blocks anything matching destructive patterns the rules don't cover. At 5:58, it's the hook that catches the rm -rf variant and logs the refusal.

The honesty box You also learned hooks' weakness this week: they fail open. You typo'd the hook's path in one settings file and it just… didn't run. Silently. So the architecture is deliberate: permissions are the guarantee; hooks are the tripwire and the recorder; CLAUDE.md is the culture. Each layer catches what the others can't.

The aftermath

Priya reads .audit.log over your shoulder — the near-miss, refused and recorded — and for the first time all story says more than one word: "Make this the template for every repo we have."

Marco, to his credit, takes it well. "So the file protected me from myself?" "No," you say. "The rules did. The file just told you they existed."

Your turn — the chapter's hands-on

Do it in your real repo
  1. Write .claude/settings.json with allow / ask / deny layers; include the push-to-main deny and something protecting your data file.
  2. Prove the evaluation order: add a narrow allow under a broad deny for the same tool; confirm deny wins.
  3. Add a PreToolUse audit hook (log every Bash command; exit 0). Deliberately break its path once and observe the silence — fail-open, witnessed.
  4. Fix the path; attempt a forbidden command; confirm refusal + log entry.
  5. Commit settings and hook; clone fresh elsewhere; verify denies apply before trust, allows after.

Checkpoint: three-layer defense committed and proven by attempted violation (a refused command, a log entry, a witnessed fail-open). Report it — next chapter, two features land on the same Friday, and Tracker learns to be in two places at once.
