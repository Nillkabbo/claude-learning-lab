Lesson 0003 · Phase 1 — The API core

Output control: max tokens, stop reasons & the dials that replaced temperature

Generation doesn't just "end" — it ends for a reason. Your code should know which one.

≈ 12 minutes Exam: Prompt Engineering · 20% No coding needed
The switchboard: five reasons generation stops — each one tells your code what to do next.

Lesson 0002 controlled the voice before generation. Today you control generation itself: how long it runs, why it stops, and what the modern dials are — because the most famous dial of all, temperature, is now deprecated. Migrations like this are pure architect-exam material.

The stop_reason switchboard

Every response carries a stop_reason — the API's control-flow signal. It's not trivia; it's what your code branches on:

stop_reasonMeansWhat your code does
end_turnModel finished naturallyUse the output
max_tokensYou cut it off mid-thoughtRaise the cap, continue, or redesign — the output is truncated
stop_sequenceA custom stop string matchedTake over: parse, continue, or hand off — a stop_sequence field reports the matched text
tool_useModel wants a tool calledExecute and loop (Lesson 0005)
refusalModel declined on safety groundsRoute to your safety/escalation path — don't retry blindly

The exam-grade insight: a truncated answer is usually a max_tokens problem, not a model problem. "The model got lazy / forgot the conclusion / cut the JSON in half" — check the stop reason before blaming the model.

max_tokens: the required dial

Still required, still the cap on generated tokens. Three architect-grade facts:

  • Undersizing is silent. The response simply ends, stop_reason: "max_tokens", and half a JSON payload in content. Budget for the task's full output, not its average.
  • The thinking budget counts against it. With extended thinking enabled, budget_tokens (minimum 1,024) comes out of your max_tokens — a classic "why is my visible answer truncated?" trap.
  • max_tokens: 0 pre-warms the prompt cache without generating — a cost-engineering move you'll revisit in Phase 4.

stop_sequences: the manual brake

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "stop_sequences": ["\nUser:", "END_OF_REPORT"],
  ...
}

Pass an array of custom strings. If the model produces one, generation halts, stop_reason becomes "stop_sequence", and the response's stop_sequence field holds the matched text. Uses: multi-part generation (stop after section one, do work, continue), delimiting machine-readable spans, and turn-taking controls in conversational systems.

Temperature: retired

Deprecated — the exam will test this migration Models released after Claude Opus 4.6 accept only temperature: 1.0. Any other value returns a 400 error. top_k is likewise rejected, and top_p only accepts ≥ 0.99 (compatibility mode). Legacy code sending temperature: 0 breaks outright on modern models — recognize it on sight.

Two things to remember about the old dial, because half the exam's distractors live here:

  • Even temperature: 0 was never deterministic — lower values made outputs more consistent, not identical. Anyone promising exact reproducibility was wrong in 2025 and is wronger now.
  • Consistency now comes from prompt structure: precise format specifications, concrete examples ("more effective than abstract instructions"), retrieval grounding, prompt chaining — and, for anything schema-shaped, structured outputs (Lesson 0004).

The new dials: thinking and effort

What replaced temperature's slot in the mental model are depth controls, not randomness controls:

DialValuesTrades off
thinkingdisabled · enabled (with budget_tokens) · adaptiveReasoning depth vs latency and tokens (budget counts against max_tokens)
output_config.effortlow · medium · high · xhigh · maxReasoning depth vs latency and cost
Scope note Effort controls how hard the model reasons, not how long the answer is — on current Opus models, long responses don't reliably shrink by lowering effort. For shorter answers, prompt for conciseness. We'll go deep on thinking and effort in Phase 4's cost/latency lesson.
The win You can now triage any failed generation like an architect: read stop_reason first (max_tokens? truncate-bug. refusal? policy path. stop_sequence? your brake fired), spot the deprecated-parameter 400 instantly, and name the modern consistency tools for each case.

Your turn

Exercise — fix the migrated report generator

A report generator ran fine on an old model. After migrating to claude-sonnet-4-6, two symptoms appear: some requests fail outright with a 400; the ones that succeed return reports that end mid-sentence. The request:

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 512,
  "temperature": 0,
  "system": "You are Apex Airlines' analytics assistant. Output the daily report as JSON.",
  "messages": [ { "role": "user", "content": "Generate today's daily ops report." } ]
}

On paper: (1) explain the 400s, (2) explain the mid-sentence endings (name the exact stop_reason), (3) fix the JSON requirement properly.

Check your answer

(1) temperature: 0 is a 400 on post-Opus-4.6 models — delete the parameter (or set 1.0). The dial is retired; consistency must come from elsewhere.

(2) stop_reason: "max_tokens" — a 512 cap can't hold a daily report. Raise it to fit the task's full output, and note that if thinking is ever enabled, its budget eats into this same cap.

(3) "Output the report as JSON" as a system-prompt sentence is advisory, not enforced — the proper fix is structured outputs (output_config.format with a schema), which guarantees compliance. If you also said "and stop blaming the model for truncation," you've internalized today's win.
