Two features, one Friday

In which tags and search land together, and nobody's merge conflict survives the weekend.

≈ 10 minutes + hands-on Concepts: worktrees · parallel sessions · clean merges Project gains: tags + search, merged without tears
Chapter 8 of 12 — the story so far.

The collision

Two features, both due Monday, both touching tracker.py: you're building search (find tasks by text), Marco is building tag (labels like #infra). Last time two people edited the same file all week, Friday ended in a merge conflict so biblical that Priya still refers to it as "the incident."

This time you know the move. Worktrees: the same repo, multiple working copies, each on its own branch — parallel sessions that structurally cannot trample each other's files.

git worktree add ../tracker-search -b feat/search
git worktree add ../tracker-tags   -b feat/tag
cd ../tracker-search && claude      # your session, its own checkout
cd ../tracker-tags   && claude      # Marco's session, its own checkout

Two Claudes, two rooms

And here is the quiet revelation of the chapter: in each worktree, your session's context is yours. Your search session never sees Marco's half-finished tag code; his never sees yours. Each Claude works a clean, complete world. Your context stays small (the budget law, working for you), and your diffs stay pure.

You build search the way you now always build: plan mode first ("how should search match — substring, case-insensitive, across tags later?"), amend the plan once, then small asks, read diffs, tests alongside. Across the hall, Marco — coaching his session with embarrassing competence now — does the same with tags. The one thing you both respect: merge order is decided by design, not seniority — you merge search first because tag matching will use search.

Friday, 3 p.m. — the merge

Search merges clean (small diffs, single-purpose commits — your habits paying out). Tags rebases onto it, and the one overlap — both touched the command dispatch — resolves in four lines, because both sides had kept their edits narrow on purpose. CI runs the suite. Green. v0.3 ships via /release, which refuses nothing this time, almost disappointingly.

What just happened, named Worktrees give every parallel effort its own checkout and its own clean context; isolation makes merges boring — and boring merges are the goal. The pattern scales up to agent fleets later (same law: isolation before parallelism).

Your turn — the chapter's hands-on

Do it in your real repo
  1. Create two worktrees on two feature branches (feat/search, feat/tag); open a Claude session in each.
  2. Build search in one (plan first: matching semantics; then implement + tests). Build tags in the other (tracker tag 3 infra, list shows tags; search can match them).
  3. Merge in dependency order; keep each conflict resolution under ten lines.
  4. Run the full suite in the main checkout; /release v0.3.
  5. Clean up: git worktree remove both.

Checkpoint: search + tag shipped, merged with (at most) one tiny conflict, v0.3 tagged. Report it — next chapter, the review queue fills up, and Tracker's PRs start reviewing themselves.
