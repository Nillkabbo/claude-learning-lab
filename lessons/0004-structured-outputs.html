Lesson 0004 · Phase 1 — The API core (final lesson of the phase)

Structured outputs: forcing shape on the answer

A guarantee, not a hope — the API mathematically cannot emit schema-invalid JSON.

≈ 12 minutes Exam: Prompt Engineering · extraction & validation No coding needed

For three lessons, every dead end has pointed here. "Output JSON only" as a system-prompt sentence? Advisory. Prefilling {? Retired — 400 error on modern models. temperature: 0 for consistency? Also a 400. Today you learn the thing that replaced them all — and why it's stronger than any of them ever were.

The mechanism: constrained decoding

Structured outputs work by grammar-constrained sampling: your JSON schema is compiled into a grammar, and the model's token choices are constrained to that grammar while it generates. Compliance isn't checked afterward — it's enforced during. The result: responses are always valid, type-safe, and need no retries for schema violations.

  THE RELIABILITY LADDER (weaker → stronger)

  "Please output JSON."        prompt instruction      advisory — the model can still drift
  prefill "{"                  legacy hack             retired — 400 on Claude 4.6+
  temperature: 0               consistency ritual      deprecated — 400 on new models
  ──────────────────────────────────────────────────────────────────────────────────
  output_config.format         constrained decoding    guaranteed — cannot be invalid

The two dials

Structured outputs are actually two independent, combinable features:

  • JSON outputs — constrain what Claude says: set output_config.format to {"type": "json_schema", "schema": {…}}.
  • Strict tool use — constrain how Claude calls functions: set "strict": true on a tool definition to guarantee schema validation on tool names and inputs (this pays off big in Lesson 0005).

Here's the proper fix for Lesson 0003's broken report generator:

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 2048,
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "report_date":  { "type": "string", "format": "date" },
          "flights_delayed": { "type": "integer" },
          "top_reason":    { "enum": ["weather", "crew", "mechanical", "air_traffic"] }
        },
        "required": ["report_date", "flights_delayed", "top_reason"]
      }
    }
  },
  "messages": [ { "role": "user", "content": "Generate today's daily ops report." } ]
}

The raw response contains valid JSON in its text content block — extract and json.loads it yourself — or use an SDK helper (client.messages.parse()) to get a parsed_output that's already a typed object (Pydantic in Python, zod in TypeScript).

Migration trap (the exam loves these) The parameter moved: old code's output_format is now output_config.format, and beta headers are no longer required. The old shape is still accepted on the wire, but the Python SDK v1.0+ raises a TypeError if you pass output_format to the beta endpoint. When you see output_format in legacy code, that's your cue.

What the schema can — and cannot — say

The grammar enforces structure, not meaning. Know both columns cold:

Supported by constrained decodingNOT supported → 400 error
Basic types; nested objects & arraysNumerical constraints (minimum, maximum, multipleOf)
enum (scalars only), const, defaultminLength / maxLength on strings
anyOf; internal $ref / $defsRecursive schemas; external $ref; allOf with $ref
String formats: date, date-time, email, uri, uuid, …enum with complex types
minItems — only values 0 and 1Array constraints beyond that; additionalProperties ≠ false

So who enforces "delay minutes must be under 300" or "airport code is exactly three letters"? Your code, after parsing — that's semantic validation, and it's a named competency in the architect exam's extraction-and-validation area: schema shape (guaranteed by the grammar), semantic rules (your code), and human review for high-stakes or low-confidence cases. Three layers, three different owners.

The bill: latency and cost trade-offs

  • First use of a schema is slower — the grammar compiles. Compiled grammars are cached for 24 hours from last use.
  • Cache invalidation rules: changing schema structure or the tool set invalidates it; changing only name or description fields does not.
  • Slightly more input tokens — Claude receives an injected system prompt describing the format; and changing output_config.format invalidates your prompt cache.
  • Streaming works, but accumulate the full response before deserializing — partial JSON isn't parseable.
The win — Phase 1 complete You can now replace every "hope it returns JSON" pattern with a guarantee, explain why it's guaranteed (constrained decoding, not checking), route each validation concern to its proper owner (grammar / your code / human review), and predict the latency and cache behavior of the change. That's the full API core: request anatomy, system prompts, output control, and enforced shape.

Your turn

Exercise — schema the delay extractor (exam-style)

Apex Airlines wants to extract structured data from delay reports. Required output per report: flight number, departure airport code (exactly three letters), delay in minutes (must be 0–300), reason, and the extractor's confidence.

On paper: (1) write the schema using only what constrained decoding supports (reason is one of: weather, crew, mechanical, air_traffic); (2) list which of the italicized rules the grammar cannot enforce and who owns them instead; (3) decide what should trigger human review.

Check your answer

(1) Types + enum + required are all grammar-supported: flight_number (string), airport_code (string), delay_minutes (integer), reason (enum of the four values), confidence (number). Everything required.

(2) "Exactly three letters" needs minLength/maxLength — unsupported (400). "0–300" needs minimum/maximum — also unsupported. Both are semantic validation: enforce them in your code after parsing, and reject or flag violations rather than retrying (the grammar already guaranteed the shape).

(3) Human review belongs where stakes are high and confidence is low — e.g. confidence below a threshold, or extractions feeding compensation payouts. If you also said "keep the original text alongside the extraction for provenance," that's exactly the exam's provenance concept: outputs should be traceable to their source.
