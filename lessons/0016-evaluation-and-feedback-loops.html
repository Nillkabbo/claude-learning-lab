Evaluation & feedback loops

The loop that makes iteration safe — criteria first, graders second, humans last (but always).

≈ 15 minutes Exam: Agentic Architecture · 27% + the exam guide's validation area

0013 demanded "extensive testing" before agent complexity; 0015 showed why agents break traditional testing — identical inputs legitimately take different paths. Evaluation is the missing pillar: without it, every prompt change is a coin flip dressed as progress. Today: how the officials say to build the feedback loop.

Success criteria come first

Before any grader exists, the target does — specific, measurable, achievable, relevant:

  • Specific: "accurate sentiment classification," not "good performance."
  • Measurable, with numbers: the docs' own examples — F1 ≥ 0.85 on 10,000 held-out tweets; fewer than 0.1% of 10,000 outputs flagged for toxicity; 95% of responses under 200ms. Even fuzzy dimensions (safety, ethics) get quantified.
  • Achievable: anchored to benchmarks and prior experiments — targets beyond frontier-model capability are theater.
  • Relevant: citation accuracy matters for a medical app, not a casual chatbot. "Most use cases need multidimensional evaluation" — pick dimensions from the menu: task fidelity, consistency, relevance, tone, privacy, context utilization, latency, price.

The cross-model rule Every LLM-graded example in the official docs notes it: use a different model to evaluate than the model that generated the output. Same-model judging inherits the generator's blind spots — the grader that made the mistake can't see it.

Design principles, and the loop

  • Mirror the real distribution — edge cases included: sarcasm, mixed sentiment, typos, rambling input, irrelevant info, ambiguity.
  • Automate the grading — multiple-choice, string match, code-graded, LLM-graded — so the loop can run without a human in it.
  • Volume beats handmade polish: many questions with lower-signal automated grading outperforms fewer hand-graded ones.
  • The loop itself: test cases → preliminary prompt → iterative testing and refinement → final validation on held-out data → ship. "This cycle is central to prompt engineering" — it's 0002's success-criteria-first discipline, closed into a circuit.

Agent-grade evaluation (from 0015's source)

  • Start small, immediately: ~20 queries of real usage patterns. Early changes move success rates 30% → 80%; you don't need hundreds of cases to see that. Teams that wait for big evals ship blind.
  • Judge outcomes, not paths: agents take different valid paths to the same goal — evaluate "whether they achieved the right outcomes while also following a reasonable process."
  • State-mutating agents: evaluate end states at discrete checkpoints (specific state changes that should have occurred), not every intermediate step.
  • LLM-judge design that worked: a single judge call scoring 0.0–1.0 plus pass/fail against a rubric — factual accuracy, citation accuracy, completeness, source quality, tool efficiency — beat multi-judge setups for consistency and alignment with humans.
  • Humans catch what automation can't: Anthropic's human testers found agents preferring SEO content farms over authoritative PDFs — a source-selection bias no automatic grader flagged. Manual testing stays essential.
The win You can build an eval suite end-to-end: numeric success criteria chosen per dimension, the right grader from the spectrum (judged cross-model), volume-optimized automation, outcome-based treatment for agents, a ~20-case starter set, and a defined role for humans. That's the "evaluation, feedback loops" exam area complete.

Your turn

Exercise — eval the 0014 pipeline (exam-style)

Recall the Q&A pipeline you composed in 0014 (route → chain w/ gates → vote → premium polish). Design its eval suite:

On paper: (1) four success criteria with numbers, one per concern (routing quality, grounding, safety, latency); (2) the grader for each, from the spectrum; (3) your first test set — what's in the ~20 cases; (4) what humans review that automation can't.

Check your answer

(1) e.g. routing accuracy ≥ 98% on a labeled 500-ticket set; ≥ 95% of claims carry verifiable citations (grounding gate pass rate); harmful-content escape rate < 0.1% at the 2/3 voting threshold; p95 latency < 3s standard tier. Numbers anchored to benchmarks where possible — the shape matters more than the values.

(2) Routing: exact match vs. labels (categorical, normalized). Grounding: LLM-binary judge ("does each cited source support its claim?") — implicit, context-dependent. Safety: LLM-binary on drafted answers (subtle violations), tuned against the voting threshold. Latency: programmatic timers. And every LLM judge runs on a different model than the drafting model.

(3) ~20 real-distribution queries with the edge cases named in the docs: ambiguous category tickets (routing stress), sarcasm, typo-laden questions, regulated-data examples (privacy route), abusive inputs, and a couple of premium-tier polishing cases.

(4) Human review for source-selection bias (the content-farm failure mode), tone on the premium tier, and sampling rejected answers for mis-voting patterns. If your criteria came before your graders — in writing, not just intent — you've got the discipline this area grades.
